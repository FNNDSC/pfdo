= pfdo: architecture
:toc:

== Abstract

pfdo is three small modules over pftree: `models` adds pfdo's options to pftree's and re-exports pftree's models, so that a tool built on pfdo imports from one place, `pfdo` adds the file-index rule and the demonstration callbacks to pftree's engine, and `__main__` adds pfdo's options and manual pieces to pftree's and assembles a command. Nothing in pftree is reimplemented; everything pfdo adds is exposed for the next layer the same way pftree exposed it.

== Options

`PfdoOptions` subclasses `TreeOptions` as a dataclass, adding `analyzeFileIndex` with its own validation and `testRun`. Because `TreeOptions.fromDict` iterates the fields of the class it is called on and ignores unknown keys, `PfdoOptions.fromDict(vars(args))` accepts the full argparse namespace of a pfdo command, and a namespace from a package below pfdo passes through in turn. pftree's own `--test <seconds>` is not exposed by pfdo; pfdo's `--test` is a flag that maps to `testRun`, and the two names do not meet.

== The file-index rule

`fileIndex_select(files, spec)` is a pure function, kept outside the class so that it can be tested as a table and used by any caller. The middle of an odd list is `len // 2`, which 5.x got wrong by rounding; an integer index is taken modulo the length, which gives the documented wrap in both directions in one expression where 5.x looped. `Pfdo.filesToAnalyze(node)` applies the rule from the options to a node's files and is the method subclasses call.

== The engine

`Pfdo` inherits the scan, the filters and `tree_process` unchanged. Its own callbacks pass through: read lists a directory's files, analyze selects by index and returns the names, save writes nothing; the demonstration pair that prefixes names and touches files runs only under `--test`. `callbacks_run` hands `tree_process` only the stages the subclass overrides, detected by comparing the method on the subclass with `Pfdo`'s own, so a tool that only analyzes never has a save stage near its output tree and never has to know one exists. `run()` checks the environment, probes and constructs the tree, filters it, and processes it when any callback is overridden, when `processAlways` is set, or when `testRun` asks. The result is pftree's `RunResult`; pfdo introduces no result type of its own because it produces nothing pftree's does not already describe.

The save demonstration shows the failure contract: an existing output file, absent `--overwrite`, returns a `StageResult` with `status` False for that directory and the run continues; the 5.x loop broke out and left the directory partly written, with the error printed in a box and the status set but the loop's other files untouched.

== The decorator surface

`pfdo.tool` attaches a task to the frame without a subclass. A `Tool` holds the option values the decorator was given and a dictionary of stage functions; `@tool.read`, `@tool.analyze` and `@tool.save` register a function under its stage name and return the function unchanged, so it stays callable and testable on its own. `analyze(**defaults)` is the one-stage shorthand: it builds a `Tool` named after the function, registers the function as its analyze stage, and returns the `Tool`, so the decorated name is the tool.

`engine_build` is where the two attachment styles meet. It builds a `Pfdo` subclass with `type()`, defining only the callbacks whose stages were registered, each a closure that calls the registered function; the analyze closure first creates the directory's `outputPath` and applies `filesToAnalyze`, so the function receives `read.files` already selected, which is the one thing a subclass has to remember to do and a function cannot. Because the subclass defines only the registered callbacks, `Pfdo.callback_isOverridden` sees exactly those, and the rule that only overridden stages run, and that overriding one is enough to process, holds without the decorator knowing it exists. The engine is instantiated per run with the run's options; nothing is cached, since a `Tool` may be run on several trees with different overrides.

A `Tool` is called three ways, and `__call__` dispatches on the arguments. With none it is the command: `parser()` builds pfdo's parser through `parser_build(standalone, command, version)` with the tool's name and `set_defaults` from the decorator's keywords, so `--help` shows them as the defaults and the command line overrides them; `main` parses, handles `--man` and `--synopsis`, configures logging, runs, reports as `pfdo`'s own `main` does, and returns the exit status. With two arguments it runs from Python: the decorator's defaults, then the call's keyword overrides, then the two directories, through `PfdoOptions.fromDict`, and the `RunResult` comes back. With a `Namespace` and two directories it is a ChRIS plugin's main: the namespace over the defaults, the positional directories set, and the exit status returned; this is the call `@chris_plugin` makes.

For that last form the `Tool` carries a `__signature__`, built from `inspect.Parameter` objects with `argparse.Namespace` and `Path` as real annotations rather than strings, so that chris_plugin's inspection, which compares annotation objects, recognises a DS plugin. `inspect.signature` reads `__signature__` before anything else, so the `Tool`'s own `__call__` signature is never seen. `functools.wraps`, which chris_plugin applies, copies `__name__`, `__qualname__`, `__doc__` and `__module__` from the tool, and the shorthand sets those from the function. A ChRIS plugin is therefore `chris_plugin(parser=tool.parser(standalone=False), ...)(tool)`, and a test in the suite runs exactly that with chris_plugin's `singleton=False` so the registry is not touched.

== The command and the manual

`parser_build(standalone, command, version)` composes pftree's `parserIO_build()` and `parserCore_build(command, version)` with pfdo's `parserSelf_build()`; the `standalone` flag omits the I/O parent for a ChRIS plugin that supplies positional directories, and `command` and `version` let a tool built on pfdo answer `--help` and `--version` as itself. `synopsis(command=...)` composes pftree's `CLI_*` and `ARGS_SYNOPSIS_*` texts with pfdo's own into NAME, SYNOPSIS, DESCRIPTION, ARGS and EXAMPLES, and takes the command's name so that a package below pfdo prints its own. `manual_build()` wraps the result in a `pftree.manual.Manual` with pfdo's banner, and `manual_print` renders it. The assembled `CLI_FULL`, `CLI_DS`, `ARGS_SYNOPSIS_FULL` and `ARGS_SYNOPSIS_DS` strings are module constants for the same reason pftree's are.

== Verification

The tests cover the file-index rule as a table, the demonstration run on the fixture of the 5.x test (two subjects, filtered to the `aparc` `mgz` files, three `analyzed-` files touched), the middle index, the overwrite refusal and its override, the leaf template, a subclass with `processAlways`, and the command through `main`. The decorator tests run the same conversion by decorator and by subclass and compare the records and the output trees; check the tool's name and plugin signature; `read.files` under `--analyzeFileIndex`; run-time overrides over the decorator's defaults; a save stage after an analyze stage, only when registered, with the payload carried between them; a read stage; a raising stage dropping its directory while the run continues; the command form parsing flags with the decorator's keywords as defaults, `--help` and `--version` naming the tool, and the exit statuses; the plugin form from a parsed namespace; the tool under `@chris_plugin` itself; and the arity error. Continuous integration mirrors pftree's: ruff and the suite on CPython 3.11 through 3.14 and 3.14t, publication on a `v*` tag.
